# 01. 仓库地图与阅读方法

大项目最难的第一步通常不是语法，而是不知道从哪里开始读。本章先建立“地图”，再给出几条真实调用链。

## 1. 顶层目录

```text
union-rust/
├── Cargo.toml              Rust workspace 清单
├── Cargo.lock              Rust 依赖精确版本
├── README.md               项目入口说明
├── DOCUMENTATION.md        完整参考手册
├── CONTRIBUTING.md         开发与提交约定
├── SECURITY.md             安全策略
│
├── protocol/               Server 与 Agent 共用的 JSON 类型
├── server/                 Linux Server，Cargo 包名 unionc
├── agent/                  跨平台 Agent，Cargo 包名 unionc-agent
├── web/                    React + TypeScript 管理台
├── tools/                  可重复的本地开发入口
├── docs/                   唯一文档索引、参考、手册、示例与历史资料
└── beginner-guide/         你正在阅读的课程式教程
```

根目录 `Cargo.toml` 把三个 Rust 包组成 workspace：

```text
unionc-protocol ← unionc-agent
        ↑
      unionc
```

箭头表示依赖共享类型。Server 与 Agent 不直接依赖彼此的业务实现，它们只共享 `protocol` 中的线上 DTO。

## 2. Server 地图

```text
server/src/
├── main.rs                 命令行入口、日志、监听、关停
├── startup.rs              启动编排与后台任务
├── state.rs                跨模块共享 AppState
├── error.rs                统一错误和 HTTP 映射
├── lib.rs                  crate 对外模块与 Linux 平台约束
├── config/                 环境配置与运行设置
├── http/                   路由组合、鉴权与安全中间件
├── auth/                   登录、会话、改密
├── system/                 健康、本机资源、SSE、审计查询
├── monitoring/             Agent 配对、上报、主机与历史；http/model/store 再按职责分目录
├── sunshine/               Sunshine 配置、探测、API 代理
└── infra/                  SQLite、路径、密钥、网络、HTTP 客户端
```

项目采用“按功能组织”而不是“控制器/服务/仓库三层横切”。例如，要理解监控功能，优先连续阅读：

1. `server/src/monitoring/mod.rs`：模块导出；
2. `model/mod.rs` 与 `model/validation.rs`：请求、响应、校验、派生指标；
3. `http/mod.rs`、`http/agent.rs`、`http/console.rs`：按信任边界组合路由与 handler；
4. `store/mod.rs` 与 `store/rows.rs`：SQLite 读写、事务和行映射。

## 3. Agent 地图

```text
agent/src/
├── main.rs                 极薄的可执行入口，只转交给 agent_app
├── agent_app/              CLI、服务启动、采样与投递编排
├── lib.rs                  库入口和模块声明
├── config.rs               配置文件、环境变量、CLI 与校验
├── model.rs                对共享协议类型的使用与辅助模型
├── collectors/             通用采样和平台采集器
├── pairing/                可恢复配对状态机、HTTP 客户端、状态与本地提交
├── spool.rs                断线报告队列
├── transport.rs            HTTP、TLS、ACK 和错误分类
├── otlp.rs                 可选 OTLP protobuf 编码
├── atomic_file.rs          原子文件发布
├── private_fs.rs           私有目录和权限
├── state_lock.rs           状态目录并发锁
├── service.rs              服务生命周期适配
├── tray_support.rs         Windows 托盘共用逻辑
├── windows/                Windows 托盘 UI/Win32 与 MSI 维护实现
└── bin/                    Windows 托盘与维护程序的极薄入口
```

平台特有实现通过 `#[cfg(...)]` 在编译期隔离。例如 Linux 温度、Linux GPU、Windows GPU、NVIDIA 分别在独立文件中。读 Agent 时先理解通用采样，再选与你的平台有关的采集器。

## 4. Web 地图

```text
web/src/
├── main.tsx                React 挂载、QueryClient、错误边界
├── app/                    登录门、导航、顶层查询、SSE 与样式入口
├── features/               按 auth/monitoring/sunshine/logs/settings 等功能聚合
│   └── <feature>/          视图、API、类型、缓存键、样式与相邻测试
└── shared/                 通用 HTTP 客户端、路径、UI、格式化与基础样式
```

这个前端没有引入通用路由库。普通管理页面由 `app/App.tsx` 中的 `view` 状态切换；只有公开 Agent 激活页会解析浏览器路径。

## 5. 数据定义放在哪里

不同问题有不同“权威来源”：

| 想知道什么 | 先看哪里 |
|---|---|
| Agent 报告、配对和 ACK JSON 有哪些字段 | `protocol/src/report.rs`、`protocol/src/pairing.rs` |
| Server 还会做哪些输入校验 | `server/src/monitoring/model/mod.rs` 与 `validation.rs` |
| 数据库当前有哪些表和约束 | `server/schema/sqlite.sql` |
| API 路径与 handler | 各功能的 `http.rs` |
| 前端实际请求哪些 API | `web/src/features/*/api.ts` 与 `web/src/shared/api/client.ts` |
| Agent 配置默认值与优先级 | `agent/src/config.rs` |
| Server 环境变量 | `server/src/config/runtime.rs` 与 `docs/server.md` |
| 依赖与 feature | 各目录 `Cargo.toml`、`web/package.json` |

文档是入口，源码与测试是最终事实。尤其是版本号、端点、限制值和 schema，不能凭记忆修改。

## 6. 四条推荐阅读链

### 6.1 浏览器读取主机列表

```text
features/monitoring/MonitoringView.tsx
  → monitoringApi.monitoringHosts()
  → GET /api/monitoring/hosts
  → monitoring/http/console.rs 路由 → http/mod.rs::list_hosts
  → monitoring/store/mod.rs::list_monitored_hosts
  → monitored_hosts + agent_metric_reports 摘要列
```

阅读时依次搜索 `monitoringHosts`、URL、handler 名和 store 函数名。

### 6.2 Agent 上报一份报告

```text
agent/src/agent_app/mod.rs 采样
  → collectors::SystemSampler
  → protocol::AgentReport
  → spool.rs 持久队列
  → transport.rs::Reporter::send_unionc
  → POST /api/agent/v1/report
  → server/src/monitoring/http/agent.rs 路由 → http/mod.rs::report_metrics
  → model/mod.rs 与 validation.rs 校验及摘要
  → store/mod.rs::store_monitoring_report
```

这条链最能代表项目核心，建议至少完整跟读一次。

### 6.3 管理员登录

```text
app/App.tsx LoginScreen
  → features/auth/api.ts::login
  → POST /api/auth/login
  → auth/http.rs::login
  → bcrypt 校验 + 内存会话
  → Set-Cookie: session + csrf
  → 后续请求经过 http/access_control.rs
```

### 6.4 Sunshine 应用列表

```text
features/sunshine/SunshineView.tsx
  → sunshineApi.sunshineApps
  → sunshine/http/mod.rs 路由
  → sunshine/http/proxy.rs handler
  → sunshine/client.rs
  → 外部 Sunshine HTTPS API
```

它与 Agent 监控链路完全不同：Server 是 Sunshine API 的受控代理，不是由 Agent 上报 Sunshine 数据。

## 7. 有效的源码阅读动作

### 先搜符号，再读上下文

```bash
rg -n "monitoringHosts" web/src
rg -n '"/api/monitoring/hosts"' server/src
rg -n "list_monitored_hosts" server/src
```

不要从文件第一行机械读到最后一行。先找到入口、调用点、类型和测试，再补上下文。

### 同时找测试

例如研究配对：

```bash
rg -n "pairing" server/tests agent/src -g '*.rs'
```

测试常比注释更精确地表达边界：什么输入应成功、什么输入必须拒绝、重复请求会怎样。

### 分清源码和生成物

初学阶段通常不需要阅读：

- `target/`：Rust 构建产物；
- `web/node_modules/`：第三方依赖；
- `web/dist/`、`web/dist.next/`：前端构建产物；
- 运行产生的 SQLite、WAL、secret 和配置文件。

它们不应作为修改入口，也不应提交到版本库。

### 用小问题驱动阅读

把“我要理解后端”改写为可验证的问题：

- `/api/health` 为什么不要求登录？
- 同一 `report_id` 上报两次为何不会多一条历史？
- SSE 断开后前端为何还能更新？
- 为什么只有最新报告保留完整 JSON？

每个问题通常只需跟踪一条链，而不是同时理解整个仓库。

## 8. 现有参考文档如何配合使用

| 文档 | 适合何时查 |
|---|---|
| `docs/README.md` | 查找项目任何当前文档时；这是唯一导航索引 |
| `DOCUMENTATION.md` | 需要完整接口、架构、数据与运维参考时 |
| `docs/reference/capabilities.md` | 判断能力等级、可选项和明确非目标时 |
| `docs/server.md` | 部署、环境变量、备份、密钥轮换时 |
| `docs/agent.md` | 平台采集、配置、投递、失败语义时 |
| `docs/agent-pairing.md` | 深挖配对协议和状态机时 |
| `docs/runbooks/agent-lifecycle.md` | 三平台安装、重装、卸载、purge 时 |
| `docs/web.md` | 前端构建与静态部署时 |
| `docs/monitoring.md` | 接入可选 OTLP 时 |
| `CONTRIBUTING.md` | 准备提交改动、运行 CI 同款检查时 |
