# 09. 认证、安全与信任边界

安全不是独立“加固层”，而是决定路由、状态码、数据结构和部署方式的系统设计。本章不替代 `SECURITY.md`，而是帮助初学者理解代码为什么看起来比普通 CRUD 更严格。

## 1. 先画出身份种类

| 调用者 | 证明身份的东西 | Server 保存什么 | 能做什么 |
|---|---|---|---|
| 管理员浏览器 | HttpOnly session Cookie | 内存会话 | 管理与查询控制台 |
| 浏览器写请求 | session + CSRF header | 会话内绑定 CSRF | 防跨站伪造写入 |
| SSE 浏览器 | 60 秒单次 ticket | 票据与签发会话关联 | 建立只读状态流 |
| Agent 配对轮询 | Pairing polling secret | SHA-256 | 只查自己的配对结果 |
| Agent 报告 | 每实例 Bearer secret | SHA-256 | 只给绑定实例上报 |
| 激活调用者 | 一次性 activation code | SHA-256 | 把一个 request 绑定到一个邀请 |
| Server → Sunshine | 配置的 Basic Auth 凭据 | AES-GCM 密文 | 代理受控 Sunshine API |
| 可信反代 | 独立 proxy secret + 网络位置 | 运行配置 | 证明请求经过预期 HTTPS 入口 |

不同 credential 不能互换。管理员 Cookie 不能提交 Agent 报告，activation code 不能读取主机，SSE ticket 不能调用普通 API。

## 2. 管理员密码

- 单管理员账号，不是多租户/RBAC；
- 密码以 bcrypt hash 存在 `unionc-config.json`；
- bcrypt 输入最多 72 字节，避免算法静默截断；
- 新密码至少 12 字符；
- hash/verify 放入 blocking task，避免阻塞 Tokio worker；
- semaphore 限制并发 bcrypt，防 CPU 资源耗尽；
- 未知用户名仍验证 dummy hash，减少基于响应时间枚举用户名。

开发首次启动可生成随机密码并打印一次。生产 bootstrap 必须显式开关与提供密码，避免数据目录指错后静默创建新管理员。

## 3. 登录限流

60 秒窗口同时考虑：

- `(来源 IP, 用户名)`；
- 来源 IP；
- 较高的全局 bcrypt 兜底。

只按用户名限流会允许攻击者锁死管理员；只按 IP 可能误伤共享 NAT；只有全局低阈值又会形成廉价全站拒绝服务。多层桶平衡防刷和可用性。

生产模式只有反代契约完整通过后才把 X-Forwarded-For 用于安全限流。当前实现只解析最后一个 XFF 头的最右项，该项必须是裸 IP；非法、为空或携带端口会返回 421，不能向左跳过并采信客户端可控值。实现假定 UnionC 前恰好一层可信反代；若再叠加 CDN 或其他代理，必须重新定义可信跳数，不能直接沿用这一假设。

## 4. Cookie 会话

登录成功后生成随机 session token 与独立 CSRF token：

- session 只保存在 Server 内存；
- 服务端绝对有效期上限为 7 天；
- session 与 csrf 都是不带 `Max-Age`/`Expires` 的浏览器会话 Cookie，关闭浏览器后失效；
- Server 重启全部失效；
- `HttpOnly` 使前端脚本不能读取 session；
- `SameSite=Strict` 降低跨站发送；
- 生产使用 `Secure` 与 `__Host-` 前缀；
- 注销删除内存会话并清 Cookie；
- 改密撤销其他会话，这些其他会话的 SSE 也随之关闭；发起改密的当前会话由前端在成功后主动注销。

会话不进 SQLite 意味着 Server 重启后必须重新登录；浏览器会话 Cookie 则保证关闭浏览器后
也必须重新输入密码。这是有意的安全与简化取舍。

## 5. CSRF 双提交

攻击者网站可能诱导已登录浏览器向 UnionC POST；浏览器会自动带 Cookie，所以“有 session”不足以证明请求来自本站页面。

UnionC 的做法：

1. Server 为每个 session 生成随机 CSRF token；
2. 令牌既保存在内存 session，也通过非 HttpOnly csrf Cookie 给同源 JavaScript；
3. `shared/api/client.ts` 对非安全方法把 Cookie 值放入 `X-CSRF-Token`；
4. Server 恒定时间比较 header 与 session 绑定值。

跨站页面不能读取本站 Cookie 值，也不能猜出随机 token。不要把它改成固定头 `1`；固定值把安全性完全寄托在 CORS 永远不放宽这一外部假设上。

GET/HEAD/OPTIONS 不应改变持久状态，因此不要求 CSRF。若新增 handler 会写数据，就不能错误地使用 GET。

## 6. SSE ticket

`EventSource` 不能添加自定义 Authorization 或 CSRF header。当前前端先用正常 Cookie+CSRF POST 取得 ticket，再用 ticket 建连；Server 同时保留无 ticket 时的管理员 Cookie 认证路径。任何情况下都不会把长期 session token 塞进 URL。

UnionC 先用正常 Cookie+CSRF POST 申请 ticket：

- 随机 UUID；
- 60 秒内必须兑换；
- 只使用一次；
- 与签发 session 绑定；
- session 注销/过期后失效；改密使其他会话签发的 ticket 失效，当前会话的 ticket 随前端紧接着的主动注销而失效；
- 建立的 SSE 也会收到 session 撤销通知并关闭。

URL 中只有短时单次 capability，而不是长期会话。

## 7. Agent credential

Agent 本地生成高熵 secret，先写私有状态；配对创建时只提交 SHA-256。正常报告会通过 HTTPS Bearer 发送原始 secret，Server 收到后：

1. 对 Bearer secret 计算哈希；
2. 按唯一 hash 查 credential；
3. 确认对应 host 仍存在；
4. 确认 body 中 host ID 与 credential host 相同。

数据库泄露时，哈希不能直接用作 Bearer credential，因为线上需要原始明文。高熵随机 secret 也使离线暴力破解不可行；这与低熵用户密码必须用慢 bcrypt 的情形不同。

UnionC 的 401 + `unauthorized` 稳定机器码表示 credential 未知，包括对应实例已经删除。当前
常驻 `run` 在下一次报告收到该机器码后会持久写入 `reauth_required`，停止投递但继续采样到
有界 spool；`once` / `doctor --delivery` 只入队并失败，不改授权状态。常驻进程重启后也不会在
创建新实例并配对前继续采样。有效 credential 与报告 `host_id` 不匹配时，Server 返回 403 +
`agent_host_mismatch`，Agent 只丢弃这一份确定无效的旧报告并继续 FIFO。通用、未知或非 JSON
的 401/403 可能来自代理/WAF，只会保留队首并退避重试。任何模式都不会自动生成新身份。

## 8. 一次性授权码

activation code 是短时 capability：

- 高熵；
- 默认 15 分钟；
- 只在邀请创建响应显示一次；
- 响应带 `Cache-Control: no-store`；
- 数据库只存 SHA-256；
- 激活端点限流；
- 一次使用，并与事务中的 request/invite 状态绑定。

它可以交给安装人员，但不能长期保存为 Agent token，也不应出现在命令日志、URL 或托盘偏好中。

## 9. 生产反向代理契约

生产拓扑要求：

```text
互联网/局域网客户端 ─HTTPS→ 可信反代 ─HTTP loopback→ UnionC
```

反代必须覆盖写入：

- `X-Forwarded-Proto: https`；
- 正确的 `X-Forwarded-For`；
- `X-UnionC-Proxy-Secret: <独立 64 位小写十六进制>`。

Server 配置同一个 `UNIONC_PROXY_SECRET`，并强制生产绑定回环。proxy secret 不能复用 AES 主密钥，也不能接受客户端自己提供/追加的值。

当前显式校验并在缺少证明时返回 421 的路径是登录、改密和全部 Agent API。其他控制台路由不逐请求检查 proxy secret，而由生产回环绑定、管理员会话和 CSRF 共同保护。421 的意思是“请求走错入口”，修好反代后原请求可以重试；403 必须结合稳定机器码解释：`agent_host_mismatch` 只丢弃不可能匹配的单条报告，其他 403 保留重试。

## 10. TLS 与可选 mTLS

Agent 支持：

- 系统信任库；
- 额外私有 CA；
- Linux PEM 客户端身份；
- Windows/macOS PKCS#12 客户端身份。

若报告入口强制 mTLS，首次配对入口必须可由尚无客户端证书的 Agent 访问，通常需要拆分 bootstrap pairing origin 与 report origin。

`pair --server URL` 会把 pairing/report 设为同一 origin。高级拆分部署应通过完整配置分别
设置 endpoint。配对成功时 Agent 会把持久化 JSON 的 `pairing_endpoint` 清为 `null`；若
服务长期设置 `UNIONC_AGENT_PAIRING_ENDPOINT`，下次加载会自动重新覆盖，否则再次配对前须
通过配置或环境变量恢复 bootstrap endpoint，才不会从 report endpoint 推导配对 URL。
Server 返回相对的 `/agent/activate/...`，Agent 又把激活 URL 绑定到 pairing origin，所以
该 origin 还必须能提供（或反代到）激活 SPA；不能只暴露配对 API。

mTLS 能证明设备持有客户端证书，但 Agent JSON 中的 host ID 仍需与 credential 绑定校验。

## 11. 输入与输出限制

| 面 | 请求上限 |
|---|---:|
| 登录/改密 | 4 KiB |
| 监控控制面/配对 | 16 KiB |
| Agent 报告 | 512 KiB |
| Sunshine 配置 | 1 MiB |
| 全局 fallback | 1 MiB |

上游 Sunshine JSON/封面也有独立流式响应上限和允许媒体类型。固定 API 端点返回的 HTTP 3xx 不会被自动跟随，避免上游把 Server 引向另一个目标。体积检查必须在完全读入内存前生效，否则“最后发现太大”已经产生内存放大。

Server 还限制字符串、数组、数值、时间和请求速率。数据库 CHECK 是最后一道粗防线。

## 12. 请求 ID、审计和日志

Server 为每个请求生成新 UUID，覆盖客户端提供的 `X-Request-ID`，并在响应回写。管理写操作的审计上下文记录同一个 ID。
若状态变更必须放入独立任务以抵抗客户端断开取消，任务要在 spawn 前捕获管理员与该 ID，
再在子任务中恢复审计上下文；Tokio task-local 不会自动继承到新任务。改密成功审计就在完成
持久化、内存发布和全部会话撤销之后由同一独立任务尝试写入，审计数据库失败只告警，不把
已经生效且无法回滚的文件配置变更伪装成请求失败。

用途：

```text
浏览器错误响应的 x-request-id
  ↔ 反代访问日志
  ↔ Server tracing 请求日志
  ↔ audit_logs.request_id
```

不要把 secret、密码、activation code、完整 Authorization 或私密配置写入日志/审计。审计 detail 必须是安全、有限、对管理员有用的状态说明。

## 13. 安全响应头

全局安全头中间件包住所有业务路由和鉴权错误响应，添加 CSP、`X-Content-Type-Options: nosniff`、frame deny、referrer policy、same-origin CORP 等；生产还包含 HSTS。请求 ID 与 Trace 层位于它外侧。

但生产静态 HTML/JS/CSS 由反代直接提供，不经过 Rust 中间件，所以反代也必须为静态响应配置等价安全头。只改 Server 不能保护静态页面。

## 14. Sunshine secret 与上游

Sunshine password 使用 AES-256-GCM 加密，密文带 key ID：

- 当前密钥只用于新加密；
- 解密按密文 key ID 选择当前或历史密钥；
- 轮换先同时加载新旧，再停服 `rekey`，最后移除旧密钥；
- 缺少对应 key 时拒绝启动，不返回乱码或清空密码。

浏览器只看到 `password_set`，不会读回明文。Server 对 host/port 做规范化，设置超时、TLS 验证选择和响应体限制。Sunshine 返回的 HTTP 3xx 不会触发对 `Location` 的请求，而会按上游失败（502）处理。开发模式允许显式 `verify_tls=false`；生产模式创建/更新配置时会拒绝该值，代理与状态读取也拒绝使用遗留的禁用 TLS 配置。它不能作为生产证书错误的解决办法。

host 语法校验不是 SSRF 目的地址隔离：当前会接受语法合法的 IP/DNS，包括回环、私网或 link-local 目标，并由 Server 直接连接。这依赖“单管理员是完全可信配置者”的当前产品边界；如果将 Sunshine 配置开放给低信任或多租户主体，必须另加 DNS 解析后地址/网段策略和重绑定防护。

## 15. 安全改动审查清单

新增端点前回答：

1. 它是公开、管理员、SSE、Agent pairing 还是 Agent report 路由？
2. 它会改变状态吗？若会，是否使用正确 HTTP 方法、CSRF 和审计？
3. 生产是否需要代理证明？
4. 请求体、字符串、集合、响应体和并发上限是什么？
5. credential 泄露后权限范围有多大，能否撤销？
6. 错误状态会让客户端采取什么行为？
7. 日志和错误消息是否泄露内部路径、SQL 或 secret？
8. 安全头是否覆盖失败响应？
9. 是否意外引入 Server → Agent 命令通道？
