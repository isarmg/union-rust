# 03. 总体架构与完整数据流

本章把此前看到的目录变成一个系统。先理解组件之间“谁信任谁、谁调用谁”，再进入具体模块。

## 1. 总体组件图

```text
                              管理面
┌──────────────┐  HTTPS + Cookie/CSRF  ┌──────────────────────┐
│ 浏览器 Web   │ ─────────────────────> │ 可信反向代理          │
│ React 静态页 │ <───────────────────── │ TLS、静态文件、转发头  │
└──────────────┘       JSON / SSE       └──────────┬───────────┘
                                                   │ 回环 HTTP
                                        ┌──────────▼───────────┐
                                        │ UnionC Server        │
                                        │ Rust + Axum          │
                                        ├──────────┬───────────┤
                                        │ SQLite   │ 后台快照   │
                                        └──────────┴─────┬─────┘
                                                       │ HTTPS
                 监控数据面                          ▼
┌──────────────────────────┐                  ┌──────────────┐
│ unionc-agent × N         │                  │ Sunshine × N │
│ Linux / Windows / macOS  │                  │ 外部上游 API  │
│ HTTPS + Bearer/JSON      │──> 上方可信反代  └──────────────┘
└──────────────┬───────────┘
               │ 可选 OTLP/HTTP protobuf
               ▼
       ┌──────────────────┐
       │ 外部 Collector   │
       └──────────────────┘
```

开发环境没有正式反向代理：Vite 提供页面并把 `/api` 代理到 Server。生产环境中，浏览器页面与管理面 API 应通过同一个 HTTPS origin 暴露；Agent 报告与首次配对入口可按 mTLS 需求单独设置，但必须在 Agent 配置中明确区分。

## 2. 四个主要组件

### 2.1 Server

Server 是中心协调者，负责：

- 管理员登录、会话与改密；
- Agent 邀请、配对、认证、上报、主机查询与撤销；
- SQLite 持久化、审计、保留期、备份与恢复；
- Server 自身资源采样；
- Sunshine 主机配置、健康探测和受控 API 代理；
- SSE 状态广播。

Server 只支持 Linux，默认只监听 `127.0.0.1:8081`。

### 2.2 Agent

Agent 安装在被监控机器上，负责：

- 只读采集本机 CPU、内存、网络、磁盘、温度、GPU；
- 在本机生成和保存长期凭据；
- 主动连接 Server，不监听远程端口；
- 断线时把报告写入有界 spool，恢复后按顺序补传；
- 可选地把数值指标同时导出到 OTLP 接收端。

它不执行 Server 命令、不下载脚本、不传输文件、不自更新。

### 2.3 protocol

`unionc-protocol` 只定义 Agent 与 Server 共用的 JSON DTO。它不采集、不校验业务范围、不访问网络、不写数据库。

这个边界很重要：共享“报文形状”可以防止两端字段和数值位宽漂移，但各端仍承担自己的职责——Agent 构造，Server 在信任边界验证。

### 2.4 Web

Web 是静态 React 应用。它：

- 不直接访问 SQLite；
- 不持久保存用户在创建/编辑表单中输入的 Sunshine 密码，也不能读回 Server 已保存的明文；
- 不接触 Agent 长期 secret；
- 所有 UnionC API 操作都通过同源 `/api` 请求 Server；打开已配置的 Sunshine `web_url` 则是明确的外部导航；
- 使用 React Query 缓存，SSE 加速状态更新，轮询兜底。

## 3. 三个“平面”

把系统按数据性质分成三个平面，会更容易判断改动放在哪里。

| 平面 | 参与者 | 凭据 | 典型数据 |
|---|---|---|---|
| 管理面 | 浏览器、反代、Server | 管理员 Cookie + CSRF | 登录、查询、邀请、撤销、Sunshine 管理 |
| Agent 数据面 | Agent、反代、Server | 每实例 Bearer secret | `AgentReport` 与 ACK |
| 可选遥测旁路 | Agent、OTLP 接收端 | 可选 OTLP token/mTLS | 时序数值，不是权威资产信息 |

Agent 数据面不经过管理员会话中间件；管理面也不能拿管理员 Cookie 冒充 Agent 报告凭据。

## 4. 信任边界

### 4.1 浏览器不是秘密保管库

浏览器可以持有管理员会话和短时一次性授权密钥，但永远不会收到 Agent 长期 secret。长期 secret 由 Agent 本地生成，Server 只保存 SHA-256 哈希。

### 4.2 Agent 报文永远是不可信输入

即使凭据有效，Agent 所在主机仍可能被入侵。因此 Server 会检查：

- token 是否属于报文中的 host；
- schema 与 Agent 版本；
- UUID 的规范格式；
- 文本长度、控制字符；
- 数值是否有限、范围是否合理；
- 数组数量与报文体积；
- 时间戳偏移。

认证回答“谁发的”，校验回答“内容能否安全接受”，二者不能互相替代。

### 4.3 反向代理是生产信任根的一部分

生产部署的所有外部流量都必须经过 HTTPS 反代。Server 会在登录、改密和全部 Agent API 上显式校验转发协议、来源 IP 与独立 proxy secret；其余控制台路由由生产回环绑定阻止外部绕过，并继续执行管理员会话与 CSRF 校验。反代必须覆盖写入这些可信头，不能透传客户端自报值。

### 4.4 Sunshine 是不稳定上游

Sunshine 可能离线、握手失败、认证失败、返回大响应或返回非预期 JSON。Server 的客户端有超时与体积上限；即使上游返回 `Location`，固定 API 请求也不会改发到另一个目标，307/308 也不会让变更请求携带原方法和请求体重放。后台探测与 HTTP 读路径分离，避免一个坏上游拖住管理台。

## 5. 完整链路一：Server 启动

```text
main.rs
  1. 初始化 tracing
  2. 解析 serve / backup / restore / rekey 等命令
  3. startup::initialize
       ├─ 固定数据目录
       ├─ 一次性读取环境配置
       ├─ 建立私有目录和单 Server 文件锁
       ├─ 初始化密钥环与管理员配置
       ├─ 创建或严格校验当前 SQLite schema
       ├─ 保留环境派生设置，加载数据库中的 Sunshine 主机
       ├─ 建立资源采样基线与 AppState
       └─ 启动后台任务
  4. http::router(state)
  5. 绑定 TCP，axum::serve
  6. 收到终止信号后优雅关停
```

顺序是安全性质的一部分。例如必须先解析数据目录，再读取管理员配置，否则错误工作目录可能被误判为首次部署。

## 6. 完整链路二：Agent 上报 CPU 指标

```text
SystemSampler 读取两次采样间的变化
  → 构造 protocol::AgentReport
  → 原子写入 state_dir/spool/*.json
  → 通知独立 delivery worker
  → Reporter 取最老报告并 POST /api/agent/v1/report
  → 反代转发给 Server
  → Axum 在 512 KiB 上限内读取原始 body
  → Server 做代理契约、匿名限流和凭据校验
  → 解析 JSON，做完整字段校验
  → 计算 CPU/内存/网络/磁盘等摘要
  → SQLite 事务幂等插入历史并推进 latest 指针
  → 返回严格 202 JSON ACK
  → Agent 核对 host_id/report_id 后删除 spool 文件
  → 可选（常驻 `run`）：已确认出队的报告进入 OTLP 有界队列
```

关键点：采样线程只做有界本地磁盘工作，网络重试由独立 worker 负责。网络再慢，也不应把下一个采样时刻向后拖。

## 7. 完整链路三：浏览器读取主机历史

```text
MonitoringView useQuery
  → api.monitoringHistory(id)
  → GET /api/monitoring/hosts/{id}/history
  → 管理员会话校验
  → 数据库健康缓存检查
  → handler 校验查询范围
  → store 按 host_id + collected_at 索引读取摘要列
  → JSON HistoryResponse
  → React Query 缓存
  → 视图把 null 显示为 N/A，把点绘成趋势图
```

历史接口不会反序列化每个完整 AgentReport。只有最新详情需要完整设备列表；历史曲线只读九个摘要数值列。

## 8. 完整链路四：登录与 SSE

登录：

```text
LoginScreen → POST /api/auth/login
  → 代理契约与按 IP/用户名限流
  → bcrypt 校验
  → Server 内存中创建 7 天会话
  → 设置 HttpOnly session cookie + 可读 csrf cookie
```

建立 SSE：

```text
useEventStream
  → 带 Cookie/CSRF POST /api/events/ticket
  → 得到 60 秒、单次、绑定会话的 ticket
  → EventSource GET /api/events?ticket=...
  → Server 兑换并删除 ticket
  → 先发送最新快照，再订阅 broadcast
  → status 事件直接更新 React Query services 缓存
```

EventSource 不能设置自定义 Authorization/CSRF 头。同源 EventSource 可自动携带 Cookie，Server 也保留该认证路径；当前前端则选择用受 CSRF 保护的 POST 换取短效单次 ticket，显式引导建连。注销或会话到期会终止该会话的连接；改密会立即终止其他会话的连接，当前前端随后主动注销发起改密的当前会话。

## 9. 完整链路五：Sunshine 管理

```text
SunshineView
  → /api/services/sunshine/hosts/{id}/apps
  → Server 根据 id 读取内存配置
  → 使用数据库解密得到的 Sunshine 凭据
  → 共享 HTTP 客户端访问 Sunshine HTTPS API
  → 不跟随 3xx，限制响应体、规范化错误
  → 返回给已认证浏览器
```

健康状态不是每个 GET 临时访问 Sunshine 得到的。唯一后台探测器维护快照：TCP 快探测约每 5 秒，API/认证慢探测约每 30 秒；配置变化会主动唤醒。

## 10. 为什么采用这些设计

### Agent 主动 POST，而不是 Server 拉取

- 被监控主机无需开放入站端口；
- 更容易穿过 NAT、防火墙和企业网络；
- 重试、幂等与断线排队语义清晰；
- 不会顺手形成命令下发通道。

### SQLite，而不是外部数据库

- 单机部署简单，自包含；
- 当前目标规模不需要分布式数据库；
- WAL 允许读写并行到一定程度；
- 代价是单写者、不能多 Server 共享、必须认真控制写事务。

### React Query，而不是手工全局 store

大部分前端状态来自 Server，React Query 已提供缓存、失效、重试、轮询和 loading/error。主题、当前页面、表单值才使用本地 state。

### SSE，而不是 WebSocket

当前需求只有 Server → 浏览器的状态推送。SSE 使用普通 HTTP、浏览器原生支持、断线恢复简单；写操作仍走清晰的普通 API。

### 完整报告只保留最新一份

历史页面只展示摘要。如果 100 台主机每 10 秒保存一份完整 JSON，30 天会产生约 2590 万份冗余大报文。当前设计保留每个时间点的数值摘要，只为详情保留最新完整报告。

## 11. 失败时谁负责什么

| 故障 | 直接表现 | 兜底/处置 |
|---|---|---|
| Server 暂时离线 | Agent 投递失败 | 报告留在有界 spool，退避重试 |
| Server 数据库忙或暂不可用 | Agent API 返回 503 + `database_unavailable` | 当前报告保留在 FIFO spool，数据库恢复后重试 |
| 报告内容永久非法 | 当前 Server 主要返回 400/409/413 | Agent 丢弃该队首，避免永久堵塞；客户端也把兼容的 422 归为永久错误 |
| Agent credential 未知、失效，或主机仍 active 但该 credential 已被重配替换/撤销 | 401 + `unauthorized` 机器码 | 当前常驻 `run` 收到 UnionC 的稳定机器码后持久写 `reauth_required`，停止投递但继续采样到有界 spool；代理/WAF 的未知 401 保持可重试 |
| 主机生命周期已撤销 | 403 + `agent_revoked` 机器码 | 当前常驻 `run` 持久写 `reauth_required`，停止投递但继续采样到有界 spool |
| 有效 credential 与报告 `host_id` 绑定不匹配 | 403 + `agent_host_mismatch` 机器码 | 只丢弃这份永远无法匹配的旧报告，继续处理 FIFO；通用或未知 403 保持可重试 |
| 反代配置错误 | 421 | 视为可重试部署故障，不误判撤销 |
| SSE 断开 | 实时指示变红 | 前端恢复 services 轮询并尝试重连 |
| Sunshine 卡住 | 慢探测或代理调用失败 | 超时、体积上限、后台快照隔离 |
| SQLite 不可用 | 依赖数据的 API 503 | readiness 失败，日志保留内部原因 |
| spool 损坏文件 | 队首无法反序列化 | 改名为 `.invalid` 隔离并纳入容量预算 |

401/403 不会由管理台主动推送给 Agent；常驻进程要等下一次报告响应才得知。一次性的
`once` / `doctor --delivery` 遇到这两类响应时只把可重试报告入队并返回错误，不改
`auth-state.json`。已写入 `reauth_required` 的常驻进程重启后，无法取得 authorized
reporter，会在进入采样循环前退出并由服务管理器重试，直到管理员完成同实例重新配对。

## 12. 永远不要破坏的产品边界

下列能力不是“以后可能补”的空白，而是明确非目标：

- Server 向 Agent 下发命令或配置；
- 远程 shell、进程控制、文件上传下载；
- Agent 在线自更新；
- 管理台动态生成或托管安装包。

如果需求要求其中任何一项，它不是普通小功能，而是安全模型和产品职责的重新设计。
