# 11. 构建、部署与运维

开发环境追求反馈速度，生产环境追求明确身份、TLS、权限、持久化和恢复。不要把 `cargo run` + Vite 当成生产拓扑。

## 1. 开发与生产对比

| 方面 | 开发 | 生产 |
|---|---|---|
| Server | `cargo run` | 发布二进制 + 专用用户 + systemd |
| 监听 | 默认回环 8081 | 必须回环，反代访问 |
| TLS | 回环可 HTTP | 外部必须 HTTPS |
| Web | Vite 从 3001 尝试，占用时可自动递增 | 构建静态 `dist/`，反代 file server |
| 管理密码 | 首启随机打印 | 显式一次性 bootstrap |
| AES 密钥 | 可在数据目录生成 | 环境提供并纳入灾备 |
| proxy secret | 开发可空 | 独立 64 位小写十六进制，反代同值 |
| 数据目录 | 可临时目录 | 固定本机私有目录 |
| Agent | CLI 临时 state | 平台包、专用服务身份、受控状态目录 |
| 日志 | 终端 | journald/系统日志 + 反代日志 |

## 2. 生产拓扑

```text
                 https://unionc.example.com
浏览器 ───────────────┐
                      ▼
                Caddy / nginx
              ┌───────┴────────┐
              │ 静态 web/dist  │
              │ /api → 8081    │
              │ TLS/安全头/SSE │
              └───────┬────────┘
                      │ 127.0.0.1
               ┌──────▼──────┐
               │ unionc      │
               │ SQLite 本盘 │
               └─────────────┘

Agent 主动使用 HTTPS 访问上方反代的 Agent API，不直连 Server 的回环端口。
```

也可以为 Agent report 和首次 pairing 使用不同域名，尤其是报告入口启用 mTLS 时，但两个
入口的 origin、证书和反代证明必须明确配置。配对成功会把持久化 JSON 的
`pairing_endpoint` 清空；长期设置的 `UNIONC_AGENT_PAIRING_ENDPOINT` 会在下次加载时重新
覆盖，否则重配对前须通过配置或环境变量恢复 bootstrap endpoint。由于激活 URL 是 pairing
origin 上的相对 `/agent/activate/...`，该域名也必须提供或反代激活 SPA，不能只开放 API。
`pairing_endpoint` 末尾不能附带 query 或 fragment，因为 Agent 还要在其路径后追加具体请求
ID 和 `/status`；租户路由需要放在 origin/path 或反代规则中。

## 3. 构建 Server

```bash
cargo build --release -p unionc
```

Linux DEB/RPM 脚本：

```bash
# 需要 Go；版本与发布工作流一致
go install github.com/goreleaser/nfpm/v2/cmd/nfpm@v2.47.0
NFPM_BIN="$(go env GOPATH)/bin/nfpm" NFPM_ARCH=amd64 server/packaging/linux/build-packages.sh
```

若 nFPM 已在 `PATH`，可以省略 `NFPM_BIN=...`；否则脚本会直接报
`nFPM is unavailable`。`NFPM_BIN` 也可以填写另一个可信的 nFPM 可执行文件绝对路径。

相关文件：

- `server/packaging/linux/unionc.service`；
- `server/packaging/linux/unionc.env.example`；
- `server/packaging/nfpm.yaml`；
- 安装/卸载脚本。

正式发布使用静态 Linux 制品并验证包内容、依赖、用户、权限、健康和备份恢复。原始二进制不包含账户、unit 和环境初始化，一般部署优先使用包。

## 4. 构建 Web

```bash
cd web
npm ci
npm run build
```

输出 `web/dist/`。脚本先构建 `dist.next`，成功后原子替换现有 `dist`；失败时保留上一个可用站点。

生产反代必须：

1. `/api/*` 转发 Server；
2. 其他路径提供静态文件；
3. 未命中静态路径回落到 `/index.html`，支持激活子路径刷新；
4. `/api/events` 关闭响应缓冲；
5. 为静态页面添加 CSP、HSTS、nosniff、frame、referrer 等安全头；
6. 覆盖而不是追加可信代理头与 proxy secret；
7. 保持 Web 与 Server 同一发布版本。

参考 `docs/examples/caddy/Caddyfile.console.example` 和 `docs/web.md`。

## 5. Server 生产环境变量

核心必填：

```text
UNIONC_ENV=production
UNIONC_DATA_DIR=/var/lib/unionc
UNIONC_SECRET_KEY=<32 字节密钥的 Base64>
UNIONC_PROXY_SECRET=<64 位小写十六进制>
```

首次部署临时增加：

```text
UNIONC_ALLOW_BOOTSTRAP=1
UNIONC_BOOTSTRAP_PASSWORD=<12 字符以上、72 字节以内>
```

管理员配置与当前 schema 数据库都创建成功后移除这两项，防止未来数据目录误指或数据库
丢失时重新 bootstrap 成看似健康的空服务。普通生产启动及 `backup`、`integrity-check`、
`rekey` 都要求既有当前库；只有 `restore` 可把已验证备份发布到缺失目标。
数据目录必须由 `unionc` 用户所有、精确 0700 且各级不是符号链接；应用不会自动 chmod
既有错误路径。首次成功认领生成的 `.unionc-data-directory` 是运行状态，卸载或恢复时应保留。

可选配置包括 bind/port、当前 key ID、历史密钥和保留期。`UNIONC_RETENTION_DAYS` 控制审计，默认 90，范围 7–3650 天；`UNIONC_TELEMETRY_RETENTION_DAYS` 控制 Agent 遥测，默认 30，范围 1–3650 天。生产值应放入权限受控的环境文件或 secret 管理系统，不写在 shell history、仓库或公开日志。

## 6. Server systemd

包安装会建立专用 `unionc` 系统用户、私有 `/var/lib/unionc` 和 hardened unit。全新安装后服务故意保持 disabled：先完成密钥、反代和一次性 bootstrap 配置，再执行 `sudo systemctl enable --now unionc`。同一版本重装只会重启原本已 enabled 的服务，不会把 disabled 安装自动启用。

`/etc/unionc/unionc.env` 中的 `UNIONC_PACKAGE_VERSION=0.3.3` 是安装脚本要求与包精确匹配的生命周期标记，不是可自由调节的运行参数，不应删除或手工改成其他版本。配置完成后检查：

```bash
systemctl status unionc
journalctl -u unionc -n 100 --no-pager
curl --fail http://127.0.0.1:8081/api/health
curl --fail http://127.0.0.1:8081/api/ready
```

ready 失败时不要只配置负载均衡继续送流量；先检查数据目录、数据库、权限、schema 和密钥，
并确认 canonical `unionc.db` 仍是启动时同一份单硬链接普通文件。路径身份异常一旦被观察到，
即使把旧文件放回也必须停服检查并重启。ready 是只读身份/schema 探测，不替代磁盘容量监控。
停止或重启服务时，Server 会先让已建立的 SSE 返回 EOF，再等待其余 HTTP 请求排空；因此
活跃管理台页面不会把 systemd 的优雅停止拖到会话过期。SSE 断开后前端先进入断线/轮询状态；
若只是瞬时流故障且会话仍有效，它会自动重连。Server 真正重启会清空内存会话，管理员需要
重新登录，随后前端才会建立新流。

管理员密码遗失需停服并用同一数据目录运行 `reset-admin-password`：

```bash
sudo systemctl stop unionc
sudo -u unionc env UNIONC_DATA_DIR=/var/lib/unionc /usr/bin/unionc reset-admin-password
sudo systemctl start unionc
```

它只改本地管理员配置，不改业务库或 Agent credential；输出的新密码只出现一次。

## 7. 构建与安装 Agent

当前官方发布制品的 feature 组合不是三平台相同：

| 官方制品 | NVIDIA | OTLP | 构建含义 |
|---|---:|---:|---|
| Linux DEB/RPM/portable | 开 | 关 | Cargo 默认 feature |
| Windows MSI | 开 | 关 | Cargo 默认 feature |
| macOS pkg | 关 | 开 | `--no-default-features --features otlp` |

手动源码构建可以选择别的组合。OTLP 被编译进二进制也不等于运行时已启用，仍需配置
`otlp_endpoint`。

### Linux

```bash
cargo build --release -p unionc-agent
# 仍要求上文安装的 nFPM
NFPM_BIN="$(go env GOPATH)/bin/nfpm" NFPM_ARCH=amd64 agent/packaging/linux/build-packages.sh
```

包安装专用 `unionc-agent` 用户、systemd unit、配置、状态目录和 purge 工具。unit 清空 capability bounding set、启用 NoNewPrivileges，并只允许私有状态目录写入。
DEB/RPM 的 root 生命周期脚本会主动把 `PATH` 重置为系统管理目录，并用绝对路径验证包内 `/usr/bin/unionc-agent`；不能让 `sudo` 或包管理器调用者的同名程序在 root 权限下被执行。
RPM 普通卸载还会把配置临时备份到 root-only 记账目录：写入和恢复都先验证目录、marker、
当前数值账户、配置和备份的类型/属主/权限/版本，再用同目录临时文件原子替换。失败时不要
删除 `config.json.remove-backup`；原子 rename 提交前可在修复信任边界后重试同版本事务，
提交后恢复配置已生效，后续服务启动失败不会回滚它。

### Windows

正式制品为 x64 MSVC MSI，包含服务、托盘和维护助手。服务使用 LocalService + 专属 service SID 保护 ProgramData credential；托盘是普通用户 UI，不负责采集。

构建/安装细节见 `agent/packaging/windows/README.md` 和 `docs/runbooks/agent-lifecycle.md`。

### macOS

正式 pkg 使用 universal binary、专用 `_unioncagent` 账户和 launchd。发布组合当前启用 OTLP、关闭 NVIDIA。脚本与日志轮转位于 `agent/packaging/macos/`。

## 8. Agent 配对不是安装

安装只把二进制、服务和私有目录放到目标机。随后仍需：

1. 管理台创建邀请；
2. 目标机 Agent 发起 pair；
3. 安装人员使用一次性授权；
4. Agent 得到稳定 instance 并保存 credential；
5. 服务开始报告。

服务处于 active 但管理台没有主机，可能只是尚未配对；这不代表服务进程失败。

## 9. Agent 权限

默认低权限能读 CPU、内存、网络和多数磁盘数据。GPU/温度可能需要设备组或平台权限。

Linux 应只把服务账户加入本机实际设备节点需要的 `render`/`video` 组，并使用提供的 GPU override。不要为了一个传感器不可见授予 root、`CAP_SYS_ADMIN` 或 `CAP_SYS_RAWIO`。

Unix 上先以服务账户运行 `probe/doctor` 检查文件和组权限。Linux shell 不会继承 systemd 的 `PrivateDevices` 等 hardening；GPU 还必须结合实际 unit、journal 和 GPU drop-in 验证。root shell 成功同样不能证明服务可见。

## 10. 卸载、purge 与撤销

三个动作语义不同：

| 动作 | Server 侧 | 本机侧 |
|---|---|---|
| Web 撤销 | 实例持久标记为 `revoked`，吊销全部 credential，保留 tombstone 和历史 | 不主动推送；文件仍在，运行中的 Agent 要等下次报告被拒才进入 `reauth_required` |
| 普通卸载 | 无变化 | 保留配置、身份、credential、spool，便于同版本重装 |
| purge | 无变化 | 永久删除本机状态与 secret |

完整退役都是先在 Web 撤销，再按平台执行本地永久清理，但命令顺序不同：

```bash
# DEB：purge 同时完成卸载和本地清理
sudo apt purge unionc-agent

# RPM：必须趁工具仍在包内时先 purge，再卸载
sudo unionc-agent-purge --yes
sudo dnf remove unionc-agent
```

Windows 必须用可信的同版本 MSI 在同一次卸载中传 `PURGE=1`：

```cmd
msiexec.exe /x UnionC-Agent-0.3.3-x64.msi PURGE=1 /qn /norestart /l*v "%TEMP%\unionc-agent-purge.log"
```

若 Windows 已经普通卸载，应先用可信的同版本 MSI 重装，再执行上述 purge。完成后还要确认
`%ProgramData%\UnionC Agent` 与固定的 `.purge-quarantine-0.3.3` 均不存在；MSI 返回成功
不单独证明 quarantine 已删除。

macOS 使用包内脚本：

```bash
sudo /usr/local/share/unionc-agent/uninstall.sh --purge
# 无人值守时才加：--yes
```

只有命令成功并完成残留验证，才能认为本地 secret 已永久删除。Windows 文件占用可能留下
quarantine；Linux/macOS 的 ownership marker 或账户属性冲突会返回非零并保留待处理内容。
修复根因后应按平台流程重试。只完成 Web 或本机一侧都会留下另一侧状态。

Linux 的账户删除凭证位于 `/var/lib/unionc-agent-package`。正常安装后该目录必须是
`root:root 0700`，其中 `managed-user` 和 `managed-group` 必须是 `root:root 0600`。purge
发现目录或 marker 是符号链接、格式/版本错误、属主改变或权限放宽时，会清掉固定位置的
Agent 状态和配置，但保留整个账户记账目录、RPM 配置备份以及系统用户/组，并以非零状态
退出；不要手工改写 marker 来强行通过，应先查清权限为何漂移，再用可信的当前版本安装包
修复或人工核对账户。
marker 不见了也不代表可以忽略：脚本必须从 NSS 明确确认对应用户或组已经不存在；若账户
仍在或 NSS 暂时不可用，会整体停止账户清理并失败。成功完成后重复执行 purge 则是安全的。

当前版本只承诺全新安装、同一 0.3.3 重装、普通卸载后同版本恢复、显式 purge；不承诺跨版本状态接管。

## 11. 在线备份

不要直接复制运行中的 `unionc.db`。包安装场景下，使用临时 systemd unit 加载与 `unionc.service` 完全相同的 data dir 和密钥环境；先确保 `unionc` 用户对目标目录有写权限：

```bash
sudo systemd-run --quiet --wait --pipe --collect \
  --uid=unionc --gid=unionc -p WorkingDirectory=/var/lib/unionc \
  -p Environment=UNIONC_DATA_DIR=/var/lib/unionc \
  -p EnvironmentFile=/etc/unionc/unionc.env \
  /usr/bin/unionc backup --output /srv/backup/unionc-$(date -u +%Y%m%dT%H%M%SZ).db
```

备份与 `.manifest.json` 成对保管，并把管理员配置、当前/历史密钥纳入异机灾备。

建议定期做恢复演练，而不是只检查备份文件存在：停服 → restore 到隔离或受控目标 →
integrity-check → 重启（重新捕获数据库身份）→ 验证 ready 与关键查询。

## 12. 恢复与版本边界

恢复会替换活动数据库，所以必须先停服。运行中的 Server 固定启动时的数据库 inode，不支持
热替换。目标已存在时需要 `--force`，但它不会绕过 manifest、SHA-256、schema、外键和密文
可解性校验；恢复后必须启动新进程重新捕获文件身份。包安装的完整命令示例：

```bash
sudo systemctl stop unionc
sudo systemd-run --quiet --wait --pipe --collect \
  --uid=unionc --gid=unionc -p WorkingDirectory=/var/lib/unionc \
  -p Environment=UNIONC_DATA_DIR=/var/lib/unionc \
  -p EnvironmentFile=/etc/unionc/unionc.env \
  /usr/bin/unionc restore --input /srv/backup/unionc-2026-08-16.db --force
sudo systemd-run --quiet --wait --pipe --collect \
  --uid=unionc --gid=unionc -p WorkingDirectory=/var/lib/unionc \
  -p Environment=UNIONC_DATA_DIR=/var/lib/unionc \
  -p EnvironmentFile=/etc/unionc/unionc.env \
  /usr/bin/unionc integrity-check
sudo systemctl start unionc
```

操作时仍要按下列顺序做人工确认：

1. 停止 Server；
2. 确认快照与 manifest 来源可信；
3. 加载正确 data dir 与密钥；
4. `restore --input ... --force`；
5. `integrity-check`；
6. 启动并验证 ready、登录、主机、Sunshine；
7. 检查命令输出并保留恢复点：健康旧库会留下可再次 `restore` 的 DB+manifest；损坏旧库可能只留下不能直接 `restore` 的 `unverified` 取证副本。若损坏库仍有 WAL/SHM，命令会保留 main/WAL/SHM 完整文件族并拒绝替换。这些文件不会自动清理；演练和异机备份确认后再按类型成对/成组清理。

只接受同一应用版本和 schema。跨版本发布前需按项目策略导出仍需数据、全新部署并重新配对，而不是指望 `--force` 绕过检查。

## 13. 密钥轮换

安全顺序如下。先编辑 `/etc/unionc/unionc.env`，使新密钥成为 current，并将旧密钥放入 `UNIONC_SECRET_KEY_PREVIOUS`：

```dotenv
UNIONC_SECRET_KEY=REPLACE_WITH_NEW_BASE64_KEY
UNIONC_SECRET_KEY_ID=2026q3
UNIONC_SECRET_KEY_PREVIOUS="2026q1:REPLACE_WITH_OLD_BASE64_KEY"
```

然后重启验证新旧密文均可读，停服并在相同环境中执行离线重加密：

```bash
sudo systemctl restart unionc
sudo systemctl stop unionc
sudo systemd-run --quiet --wait --pipe --collect \
  --uid=unionc --gid=unionc -p WorkingDirectory=/var/lib/unionc \
  -p Environment=UNIONC_DATA_DIR=/var/lib/unionc \
  -p EnvironmentFile=/etc/unionc/unionc.env \
  /usr/bin/unionc rekey
sudo systemctl start unionc
```

确认服务和 Sunshine 密文正常后，从 `unionc.env` 移除 `UNIONC_SECRET_KEY_PREVIOUS`，再执行 `sudo systemctl restart unionc`，旧密钥才算彻底退役。

若先删除旧密钥，Server 会因已有密文 key ID 无法解析而拒绝启动。这是 fail closed，不应通过清空 Sunshine password 绕过。

## 14. 监控与容量

至少监控：

- `/api/health`、`/api/ready`；
- Server 进程重启、内存、CPU、磁盘空间；
- `unionc.db`、WAL 增长和备份成功；
- Agent spool pending/invalid；
- 401/403/421/429/5xx 比例；
- Sunshine 探测失败；
- 审计/遥测保留期任务；
- 反代 TLS 到期和 SSE 缓冲。

容量粗略受：

```text
主机数 × 每日 86400 / 平均上报秒数 × 每行摘要大小 × 保留天数
```

影响。断线恢复会产生突发写；当前默认面向单 Server、约 20 台主机。扩大规模前应使用代表性报告、保留期和离线补传压测，而不是只看平稳平均值。

## 15. 可选 OTLP 部署

仓库只提供 Agent 输出，不提供 Collector、时序库、看板或多租户网关。生产启用时应：

- 显式构建 otlp feature；
- 使用 HTTPS 和可独立配置的 OTLP Bearer token；TLS CA 与客户端身份当前和 UnionC
  report/pairing 共用同一个 HTTP client，若必须使用独立客户端证书，需要网关隔离或代码支持；
- 对常驻 `run` 监控容量 128 内存队列的丢弃告警；
- 自行部署和备份接收端；
- 不把 OTLP 当作管理台权威身份数据；
- 跨租户时增加证书身份与 `host.id` 属性绑定网关。
