# 04. 共享协议与监控数据模型

Agent 与 Server 是两个独立进程。它们能正确协作的基础，是双方对 JSON 字段、类型、状态和错误语义有完全一致的理解。

## 1. 协议代码的职责

权威文件是 `protocol/src/lib.rs`。它只包含：

- 当前 `schema_version`；
- Agent 报告及嵌套 DTO；
- serde 序列化/反序列化规则；
- 规范 UUID 反序列化；
- 协议自身的往返与拒绝测试。

它刻意不包含：

- 从操作系统采集数据；
- HTTP 路由和认证；
- 数值业务范围校验；
- SQLite 持久化；
- 前端展示类型。

Server 通过 `server/src/monitoring/model.rs` 为共享类型增加信任边界校验与摘要计算。

## 2. `AgentReport` 总览

```text
AgentReport
├── schema_version          当前为 1
├── report_id               每次采样唯一 UUID
├── collected_at            Agent 采样时间（UTC）
├── host                    稳定主机身份与版本
├── interval_seconds        本次速率指标对应的实测时间间隔
├── system
│   ├── uptime_seconds
│   ├── cpu
│   ├── memory
│   ├── networks[]
│   ├── disks[]
│   ├── temperatures[]
│   └── gpus[]
├── capabilities[]          能力可用性与失败原因
└── agent
    ├── spool_pending_batches
    └── collector_errors
```

每个层级都使用 `deny_unknown_fields`。旧字段、拼错字段或未协商的新字段会被明确拒绝，不会悄悄丢弃。

## 3. 主机身份与报告身份

`HostIdentity` 包含：

| 字段 | 含义 |
|---|---|
| `id` | 配对完成后由 Server 预留的稳定 `instance_id` |
| `name` | 展示名称，可随报告更新 |
| `os` | 平台，如 linux/windows/macos |
| `os_version` | 可选系统版本 |
| `kernel_version` | 可选内核版本 |
| `arch` | 架构，如 x86_64/aarch64 |
| `agent_version` | 必须与当前 Server package 版本完全一致 |

`report_id` 与 `host.id` 不同：

- 配对完成后的 `host.id` 在一台逻辑主机整个生命周期内稳定；`probe` 每次生成的诊断 UUID
  不会持久化，不属于这个稳定身份；
- `report_id` 每份采样都不同，用于幂等去重；
- 管理员为既有 `instance_id` 创建邀请时，重新配对会换 credential，但保留 `host.id` 与历史；
- 创建不绑定既有 `instance_id` 的新邀请会得到新的主机 UUID，不能当作同一实例恢复。

## 4. 配对涉及的标识与秘密

| 名称 | 是否保密 | 谁生成 | 生命周期 | 用途 |
|---|---|---|---|---|
| `instance_id` | 否 | Server | 主机整个生命周期 | 稳定逻辑主机 ID |
| invite `request_id` | 否 | Server | 邀请生命周期 | 管理员取消邀请 |
| `activation_code` | 是 | Server | 短时、单次 | 授权某个配对请求占用邀请 |
| pairing `request_id` | 否 | Server | 配对生命周期 | 浏览器与 Agent 指向同一请求 |
| `polling_secret` | 是 | Agent | 配对完成/过期前 | Agent 私密轮询状态 |
| `agent secret` | 是 | Agent | 撤销或重新配对前 | 正常报告 Bearer 凭据 |
| `credential_id` | 否/内部 | Server | credential 记录生命周期 | 数据库管理 credential 行 |
| `report_id` | 否 | Agent | 该报告记录仍被保留期间的全局去重键 | 报告幂等与 ACK 核对 |

最重要的规则：配对创建时 Agent 只提交两个 secret 的 SHA-256。之后轮询和报告会通过 HTTPS Authorization 发送原始 secret，Server 收到后立即哈希查库；数据库不保存明文，浏览器也不会收到它们。

## 5. 配对时序

```text
管理员              Server                   Agent              浏览器
  │ 创建邀请           │                        │                  │
  ├──────────────────>│                        │                  │
  │ instance + code   │                        │                  │
  │<──────────────────┤                        │                  │
  │                   │  本地生成两个 secret    │                  │
  │                   │<──提交 host + 两个哈希──┤                  │
  │                   │──request + 激活路径────>│                  │
  │                   │                        │──打印路径；用户打开─>│
  │                   │<──核对摘要 / 提交 code────────────────────┤
  │                   │  一个事务绑定全部状态   │                  │
  │                   │<──Pairing secret 轮询───┤                  │
  │                   │──active + instance_id──>│                  │
  │                   │                        │ 按日志提交并开始上报│
```

Agent 先把未来 credential 可靠写入配对状态，再把哈希发给 Server。若反过来，Server 可能接受一个 Agent 已经因本地写盘失败而丢失明文的 credential。

服务端激活绑定是一个数据库事务；Agent 本地则是 crash-safe 的多文件提交：进入
`Activating` 后，token、host ID、配置和授权状态分别以原子文件替换幂等写入，最后才写
`Active`。因此崩溃后可继续完成，但不能把几个文件误解为一次文件系统原子事务。

## 6. 指标字段如何理解

### 6.1 CPU

- `usage_percent`：总 CPU 百分比；
- `logical_count`：逻辑处理器数，线上固定 `u32`，不使用随架构变化的 `usize`；
- `physical_count`：物理核心数，可能不可得；
- `per_core_percent[]`：各逻辑核心占用。

### 6.2 内存

内存使用绝对字节数：total、used、available、swap total、swap used。Server 计算百分比摘要，避免不同客户端各自采用不一致公式。

### 6.3 网络与磁盘

同时包含累计量和速率：

- `*_bytes_total`：自系统计数基线以来的单调累计值；
- `*_bytes_per_second`：Agent 根据两次采样差值和实测间隔得到的速率。

速率是浮点数，因为采样间隔带 jitter，不一定是完整整数秒。系统重启、接口重建或计数器回绕时，采集器必须避免产生巨大负差或假速率。

### 6.4 温度与 GPU

大量字段是 `Option`：设备可能不提供温度、显存、功耗或 PCIe 吞吐。`null` 表示不可得，`0` 表示可得且真实为零。

## 7. capability 为什么单独存在

一个空的 `gpus` 数组无法说明“没有 GPU”“驱动没装”“权限不足”还是“临时读取失败”。capability 用结构化信息表达原因：

```text
name         能力名
available    是否可用
source       采集来源
error_kind   unsupported / not_present / driver_missing /
             permission_denied / transient / invalid_data
message      给人看的补充说明
```

当前 Agent 构造器遵守的约定：

- 可用能力没有 `error_kind` 和错误消息；
- 不可用能力必须说明结构化原因；
- 前端应显示 N/A 与原因，不把缺失值画成 0；
- 新增错误类别是协议变更，Server、Agent、测试和文档必须同步。

前两项目前是采集侧构造约定，并非 Server 强制校验的不变量。若要把它们升级为协议规则，必须补 Server 校验与合同测试，不能只修改辅助构造器。

## 8. Server 的分层校验

一份报告会经过多层防线：

1. Axum 在 512 KiB 上限内有界读取原始 body；
2. 生产反向代理契约与认证前来源限流；
3. Authorization 头与 token 哈希查库；
4. 每主机令牌桶；
5. Content-Type 与 JSON 结构/未知字段；
6. `AgentReportExt::validate` 业务校验；
7. credential 所属 host 与 `report.host.id` 一致；
8. SQLite STRICT 类型、外键和 CHECK 约束。

先认证再反序列化节省的是 JSON 解析和结构化分配，不会省掉最多 512 KiB 的网络传输与原始 body 缓冲。也不能因为数据库已有 CHECK 就删除 Rust 校验：入口校验能给客户端清晰 400，并施加更细的集合大小、文本和语义限制。

## 9. 上报间隔的三层契约

修改上报周期边界时必须联合检查：

| 层 | 文件 | 约束 |
|---|---|---|
| HTTP 权威校验 | `server/src/monitoring/model.rs` | 实测间隔 `[0.1, 3600]` |
| Agent 配置 | `agent/src/config.rs` | 整数秒，至少 1；最坏 jitter 后不得超过 3600 |
| SQLite 粗防线 | `server/schema/sqlite.sql` | `0 < interval_seconds <= 3600` |

三层相关但不完全相同。只改一处会出现“Agent 能启动但每份报告都被永久拒绝”或“入口接受但数据库拒绝”的漂移。

## 10. ACK 是成功的一部分

成功报告的唯一契约是：

- HTTP 202；
- `Content-Type: application/json`；
- JSON 包含 `host_id`、`report_id`、`accepted`、`received_at`；
- `host_id` 和 `report_id` 与本次发送完全一致。

代理误路由返回的 200 HTML、空 204 或结构相似但 ID 不同的 JSON 都不是成功。Agent 只有核对完整 ACK 后才能删除 spool 文件。

`accepted=false` 不代表失败。它表示相同主机的同一个 `report_id` 之前已经持久化，常见于 Server 提交成功但首次 ACK 在网络中丢失。Agent 此时也可以安全出队。

## 11. 幂等与乱序

### 同一报告重放

`report_id` 在对应遥测记录仍被保留期间是全局主键；保留期任务可删除非 latest 旧行，因此这不是无限期重放缓存。同一 host 重放一份仍在保留的报告时：

- 不新建历史行；
- 返回首次 `received_at`；
- 不刷新 `last_seen_at`；
- 不用重放 body 覆盖身份和能力。

若同一 `report_id` 已属于另一 host，返回冲突，防止跨主机碰撞悄悄合并。

### 旧报告补传

断线后按时间顺序补传，但新的实时报告也可能先到。旧报告：

- 可以进入历史；
- 不推进 latest 指针；
- 不覆盖当前身份和 capability；
- 不把离线主机伪装成刚刚在线。

若 `collected_at` 相同，以 `report_id` 字典序作为稳定次级排序，使最终 latest 不依赖到达顺序。

## 12. 主机状态如何计算

设 `age` 为当前时间与 `monitored_hosts.last_seen_at` 的秒差。该值在实例激活时初始化，之后只由“新插入且成为 latest”的报告更新为 Server 接收时间。`interval` 取最新报告实测间隔并夹在 1 到 3600 秒；尚无报告时回退为 10 秒：

```text
online  : age <= max(interval × 3, 30 秒)
stale   : age <= max(interval × 12, 300 秒)，且已不 online
offline : 超过 stale 阈值
revoked : 生命周期已撤销，优先于时间状态
```

因此默认 10 秒周期时：30 秒内 online，5 分钟内 stale，之后 offline。动态阈值让低频 Agent 不会仅因配置周期较长被误报离线。

## 13. 报告如何变成页面数据

Server 在写入时计算九个摘要：CPU、内存、网络收/发、磁盘读/写、最高温度、GPU 使用、GPU 显存使用。

```text
完整 AgentReport ──最新一份──> payload JSON ──> 主机详情
       │
       └──每一份──> 九个摘要列 ──> 主机列表与历史曲线
```

当前 latest 更新时，上一份报告的 `payload` 会被置空，但摘要历史仍保留。

## 14. 修改协议的正确清单

新增或修改一个线上字段时，至少检查：

1. `protocol/src/lib.rs` DTO、serde 与协议测试；
2. Agent 采集/构造逻辑及各平台 `cfg`；
3. Server `monitoring/model.rs` 校验与摘要；
4. 若持久化，更新 `server/schema/sqlite.sql` 当前唯一基线和 schema 指纹测试；
5. store 的写入、读取、幂等与乱序语义；
6. `web/src/types.ts`、`api.ts`、视图与 null 展示；
7. Server/Agent 契约集成测试和前端测试；
8. 文档与版本匹配策略。

当前项目不做旧 schema 或旧 Agent 的兼容读取。协议变化不是只在 JSON 里加一行。
