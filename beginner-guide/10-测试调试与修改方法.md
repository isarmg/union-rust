# 10. 测试、调试与修改方法

“能编译”只说明类型基本一致；UnionC 还有协议、安全、事务、乱序、跨平台和前端并发等行为边界。本章给出一套可重复的修改工作流。

## 1. 测试分层

```text
                    少量：真实系统/发布门禁
                 OTLP Collector、包安装生命周期
              ────────────────────────────────
               集成测试：HTTP + 临时 SQLite
             配对、报告、认证、历史、备份恢复
          ──────────────────────────────────────
           单元/组件测试：纯函数和局部状态机
       校验、采集转换、spool、React hook、视图交互
    ───────────────────────────────────────────────
       静态门禁：fmt、clippy、typecheck、lint、build
```

越靠下越快，适合频繁运行；越靠上越接近真实环境，但成本更高。一次改动通常需要多层组合，而不是只依赖一个“全量测试”。

## 2. Rust 日常命令

### 快速反馈

```bash
cargo fmt --all -- --check
cargo check -p unionc
cargo check -p unionc-agent
cargo test -p unionc-protocol
```

### 组件测试

```bash
cargo test -p unionc
cargo test -p unionc-agent
cargo test --workspace
```

### lint

```bash
cargo clippy -p unionc --all-targets -- -D warnings
cargo clippy -p unionc-agent --all-targets -- -D warnings
```

`-D warnings` 把警告当错误，与 CI 保持一致。

CI 跟随未固定补丁版本的 Rust `stable`。本机若长期没有执行 `rustup update stable`，即使同叫
stable，也可能比 runner 旧；新版 Clippy 还可能新增默认 lint。复现 CI 静态检查失败时，先
比较 `rustc --version`，再注意 Windows/macOS 的 `#[cfg]` 代码无法由 Linux Clippy 代测。

### Agent feature 矩阵

```bash
cargo check -p unionc-agent --no-default-features --all-targets
cargo check -p unionc-agent --no-default-features --features otlp --all-targets
cargo check -p unionc-agent --no-default-features --features nvidia --all-targets
cargo test -p unionc-agent --features otlp --test otlp_encoding
```

默认构建无法覆盖“关闭 NVIDIA”“只开 OTLP”等编译分支。feature 代码若只在发布时首次编译，风险太高。`otlp_encoding` 由 `required-features = ["otlp"]` 保护，普通 `cargo test -p unionc-agent` 不会运行它。真实 Collector 合同还可在已准备接收端时显式运行：

```bash
UNIONC_AGENT_TEST_OTLP_ENDPOINT=http://127.0.0.1:4318/v1/metrics \
UNIONC_AGENT_TEST_REQUIRE_OTLP=1 \
cargo test -p unionc-agent --features otlp --test otlp_live
```

这里的 live 测试只证明 Agent → 真实 Collector 的接收合同；它不证明 Collector exporter、
时序库落库和查询链路可用。HTTP 接受成功与下游最终可查询是两道不同门禁。

## 3. 前端日常命令

在 `web/` 中：

```bash
npm ci
npm audit --audit-level=high
npm run lint
npm test
npm run typecheck
npm run build
```

- ci/audit：严格按锁文件安装，并让 high/critical 已知依赖漏洞失败；
- lint：代码与 hooks 规则；
- test：Vitest 非交互运行；
- typecheck：TypeScript 项目引用检查，不输出 JS；
- build：先 typecheck，再构建到 `dist.next`，最后原子发布到 `dist`。

build 不只是“再编译一次”，还验证 lazy chunk、静态资源和成功发布路径；发布失败时保留旧 `dist` 的回滚分支由 `web/scripts/publish-static.test.ts` 在 `npm test` 中模拟守护。

### 当前 CI 覆盖边界

| Job | workflow 配置的成功路径门禁 |
|---|---|
| `server` | Linux fmt、clippy、Server 测试 |
| `agent` | Linux/Windows/macOS 的 fmt、clippy、Agent 测试和三组 feature check；另跑各平台打包/生命周期门禁 |
| `otlp` | `otlp_live` 对真实 Collector 的接收合同 |
| `frontend` | Node 26 下的 install、high/critical 依赖审计、lint、typecheck、test、build |

表中描述工作流设计；单个 Job 的前置步骤失败时，后续步骤会被跳过，必须查看该次运行日志
确认究竟执行到了哪一道门禁。

当前 CI 没有单独执行 `cargo test -p unionc-protocol`，OTLP job 也没有执行
`otlp_encoding` 的官方 proto 解码断言。因此上面的本地命令不是重复劳动：远端全绿仍不能
替代这两项。三平台打包门禁则相反，不能用单一开发平台的本地结果替代。

`npm ci` 会打印依赖审计摘要，但发现漏洞时仍可能返回 0；因此 workflow 还会显式执行
`npm audit --audit-level=high`，让 high/critical advisory 阻断 Frontend Job。moderate/low
问题及 Rust 依赖仍需单独审查——当前没有 `cargo audit` 门禁。修复前要检查依赖路径、生产
可达性和升级影响，不能不看依赖树就直接执行可能引入破坏性升级的自动修复。

## 4. 只运行相关测试

修改时先跑最相关用例，反馈更快：

```bash
cargo test -p unionc --test agent_pairing
cargo test -p unionc --test report_ordering
cargo test -p unionc --test csrf_double_submit
cargo test -p unionc --test security_headers
cargo test -p unionc --test sqlite_maintenance
```

按测试名过滤：

```bash
cargo test -p unionc duplicate_report
```

查看测试输出：

```bash
cargo test -p unionc duplicate_report -- --nocapture
```

前端也可传 Vitest 文件：

```bash
cd web
npm test -- src/hooks.test.tsx
```

最终提交前仍要运行与影响面相称的完整门禁。

## 6. 建立安全的复现环境

不要用生产数据调试。为每次复现创建独立目录与端口：

```bash
export UNIONC_DEBUG_SERVER_DATA="$(mktemp -d /tmp/unionc-debug-server.XXXXXX)"
UNIONC_DATA_DIR="$UNIONC_DEBUG_SERVER_DATA" \
UNIONC_SERVER_PORT=18081 \
RUST_LOG=unionc=debug \
cargo run -p unionc
```

Agent 同样隔离：

```bash
export UNIONC_DEBUG_AGENT_STATE="$(mktemp -d /tmp/unionc-debug-agent.XXXXXX)"
export UNIONC_AGENT_CONFIG="$UNIONC_DEBUG_AGENT_STATE/config.json"
export UNIONC_AGENT_STATE_DIR="$UNIONC_DEBUG_AGENT_STATE"
cargo run -p unionc-agent --bin unionc-agent -- status --json
```

复现记录至少包含：代码版本、命令、环境变量名（secret 值打码）、预期、实际、时间、响应状态、request ID 和相关日志。

## 7. 使用日志和请求 ID

Server：

```bash
UNIONC_DATA_DIR="$UNIONC_DEBUG_SERVER_DATA" \
UNIONC_SERVER_PORT=18081 \
RUST_LOG=unionc=debug,tower_http=debug \
cargo run -p unionc
```

Agent：

```bash
UNIONC_AGENT_CONFIG="$UNIONC_DEBUG_AGENT_STATE/config.json" \
UNIONC_AGENT_STATE_DIR="$UNIONC_DEBUG_AGENT_STATE" \
RUST_LOG=unionc_agent=debug \
cargo run -p unionc-agent --bin unionc-agent -- doctor
```

不要在公开问题或日志中粘贴：管理员密码、session/csrf Cookie、Authorization、activation code、Agent token、pairing state、AES/OTLP secret。

HTTP 失败时记录响应的 `X-Request-ID`。它能关联反代日志、Server trace 和审计。客户端自带的 ID 会被覆盖，所以该值可信地代表 Server 处理链路。

## 8. 排错树：Server 启动失败

```text
是否 Linux？
  ├─ 否 → 只能构建 Agent/Web，换 Linux 运行 Server
  └─ 是
     ↓
日志第一行的数据目录是否正确？
  ├─ 否 → 修正 UNIONC_DATA_DIR，不要允许错误目录 bootstrap
  └─ 是
     ↓
是文件锁、schema、密钥还是端口错误？
  ├─ 锁 → 确认是否已有 Server/维护命令
  ├─ schema → 只接受当前空库/同版本恢复，不手改元数据
  ├─ key ID → 恢复对应历史密钥，不清空密文
  └─ address in use → 找占用或换明确端口
```

`/api/health` 成功但 `/api/ready` 失败时，问题在依赖/数据目录/数据库，不是监听本身。

## 9. 排错树：登录或页面失败

1. 对前面的隔离复现 Server 执行 `curl http://127.0.0.1:18081/api/health` 与 `curl http://127.0.0.1:18081/api/ready`；
2. 看 Vite 是否把 `/api` 代理到正确端口；
3. 浏览器 Network 面板看 status、Content-Type、响应 JSON 和 request ID；
4. 401：会话/密码；403：CSRF 或权限语义；421：生产代理；429：限流；5xx：Server；
5. 页面收到 200 HTML 而预期 JSON：检查 SPA/API 反代路由顺序；
6. SSE 红色但数据仍更新：可能只是流断开并已回退轮询；
7. 静态子路径刷新 404：生产反代缺少 SPA fallback。

不要把所有错误都转成登录页，否则数据库或代理故障会被误诊为用户密码问题。

## 10. 排错树：Agent 没数据

诊断已安装 Agent 时按下列固定顺序；前三个命令只读，但会读取已安装 Agent 的真实配置和状态。若是调试源码，应继续使用第 6 节已导出的隔离环境和 `cargo run -p unionc-agent --bin unionc-agent -- ...`：

```bash
unionc-agent status
unionc-agent doctor
unionc-agent probe --json
# 明确允许真实投递时才执行：
unionc-agent doctor --delivery
```

检查：

- config path 与 application version；
- endpoint / pairing endpoint / HTTPS / CA；
- host-id、credential、pairing、reauth_required；
- spool pending 与 `.invalid`；
- 401、403、421 的不同含义；
- 服务账户采集权限，而不是只看 root 的 probe；
- Server 与 Agent package 版本是否精确相同；
- ACK 是否被反代替换成 HTML。

spool 增长说明采样仍在工作、投递没有确认。先找最早的发送错误，不要直接删除队列。

## 11. 排错树：Sunshine 异常

- hosts 列表 pending：等待后台探测，确认配置变化已触发；
- reachable=false：TCP 地址/端口/网络；
- reachable=true 但 connected=false：TLS、用户名、密码、API；
- 浏览器能直接开 Sunshine 但 UnionC 不行：Server 所在网络和信任库可能不同；
- `verify_tls=false` 能“修好”：说明证书信任/名称确有问题，应配置正确证书而不是长期关闭验证；
- 更新后界面闪回旧值：检查 Sunshine mutation 屏障与 query key，而非只延长轮询；
- 大日志/封面失败：看上游体积与媒体类型限制。

## 12. 修改功能的标准步骤

### 第一步：写一句行为定义

例如：“当主机最新 GPU 温度不可得时，详情显示 N/A，并保留 capability 原因。”不要只写“改 GPU 页面”。

### 第二步：确认所有权

它属于采集、协议、Server 派生、数据库、API、前端展示还是部署？先找最小影响面。

### 第三步：先找现有测试与不变量

使用 `rg` 搜符号、URL、字段和状态。读注释中的“为什么”，特别是锁、事务、状态码和错误分类。

### 第四步：写会在旧行为下失败的测试

若测试在缺陷存在时也通过，它没有保护目标。测试名描述可观察行为，不描述方法名。

### 第五步：做最小闭环改动

避免顺手重构无关模块。协议字段改动与纯 UI 卡片改动的影响面完全不同。

### 第六步：从窄到宽验证

相关测试 → package 测试 → lint/typecheck → workspace/feature/构建门禁。

### 第七步：更新文档

行为、配置、端点、安全边界或运维顺序变化时，至少更新相应参考文档与教程。

## 13. 三类改动的影响面

### 纯展示改动

可能只需：View + 相邻前端测试。先确认 `types.ts` 已有数据，不要无谓改后端。

### 新管理端点

通常需：Server model/http/store、路由、中间件分类、CSRF、审计、body limit、错误、前端 API/type/query/view、HTTP 测试和文档。

### 新 Agent 指标

通常需：protocol、Agent 各平台采集与 capability、Server 校验/摘要、schema/store/query、Web type/display、乱序/容量/版本测试、OTLP（若导出）和文档。

## 14. 代码审查时重点看什么

- 是否改变只读 Agent 边界；
- 网络 `.await` 是否发生在全局锁/写事务中；
- 失败是否被分成永久、凭据、撤销、代理、暂时；
- `null` 是否被错误转换为 0；
- 写端点是否具备 CSRF、审计和正确方法；
- 动态 URL 是否编码；
- 查询 key 是否包含全部参数；
- 响应/请求/集合是否有界；
- 旧报告或旧 GET 是否能覆盖新状态；
- 是否按秘密类型正确处理：长期 Agent secret 和已存储的 Sunshine 密码明文不得返回浏览器，一次性授权码/CSRF/新密码等合法浏览器输入也不得进入 URL 或日志；
- 测试是否真的能捕获回归。

## 15. 工作区与提交卫生

修改前后检查：

```bash
git status --short
git diff --check
git diff --stat
```

现有未提交改动可能属于其他人，不要重置、覆盖或格式化无关文件。不要提交 `target`、`node_modules`、`dist`、临时数据库、token 或本地配置。
